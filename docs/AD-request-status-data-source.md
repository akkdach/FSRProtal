# /api/request-status ค้น SIMS ก่อน แล้วค่อย F&O — หลัง cutover F&O

บันทึกว่าทำไม `/api/request-status` เปลี่ยนแหล่งข้อมูล ตัดสินใจอะไรไปบ้าง ทางเลือกอื่นคืออะไร และผลที่ตามมา

## 1. บริบท

- F&O หยุดรับใบงานใหม่ที่ cutover (ใบงานสุดท้าย 2026-10-31 18:45 เวลาไทย) และ SIMS เริ่มใช้งานจริง 2026-11-01 ด้วยฐานข้อมูลใหม่ ไม่ได้ย้ายใบงานเก่ามา
- `/api/request-status` เดิมอ่าน Fabric (mirror ของ F&O) ผ่าน stored procedure `dbo.REFERENCEDPONUMBER` → หลัง cutover ใบงานใหม่ทุกใบตอบ `NOT_FOUND`
- มีเส้นคู่ขนาน `/api/request-status-sims` (PR #11, 2026-10-28) ที่อ่าน SIMS ด้วยสัญญาเดียวกัน พร้อมเส้นเสริม `/api/request-status-sims/order/{serviceOrderNumber}`
- ผู้เรียกใช้ path `/api/request-status` อยู่แล้ว (ผ่าน gateway)

## 2. การตัดสินใจ

| # | ตัดสินใจ | รายละเอียด |

| 2 | สลับใน **โค้ดตรง ๆ** | ไม่มีสวิตช์ใน App Settings — deploy = สลับทันที |

| 4 | สัญญาไม่เปลี่ยน รวมถึงกรณี error จาก input | key / ลำดับ / รูปแบบค่า / HTTP code / MESSAGE เดิม (รายละเอียดใน `AS-request-status.md` ข้อ 2) — ผู้เรียกไม่ต้องแก้อะไร · ข้อยกเว้น: MESSAGE ของ 500 ตอนระบบหลังบ้านล้มเป็นข้อความกลาง ๆ แทน error ดิบของ GraphQL (ไม่เปิดเผยรายละเอียดภายใน) |

เหตุผลของเจ้าของระบบ: ข้อ 1 — ผู้เรียกต้องค้นเจอใบงานทั้งจากระบบใหม่ (SIMS) และระบบเก่า (F&O) · ข้อ 2–3 _(ให้ผู้เซ็นกรอก)_

## 3. ทางเลือกที่พิจารณาแล้วไม่เลือก

| ทางเลือก | ผลทางเทคนิค |
|---|---|
| ค้น SIMS อย่างเดียว | ง่ายกว่า เร็วทุก request แต่ ticket ของใบงานก่อน cutover ได้ `NOT_FOUND` ทั้งที่เคยพบ — เจ้าของระบบเลือกทางนี้ก่อนแล้วเปลี่ยนเป็นข้อ 1 ในวันเดียวกัน |
| ค้น F&O ก่อน แล้วค่อย SIMS | ทุก request รอ Fabric (1–14 วินาที) แม้ใบงานใหม่ · ticket ที่มีทั้ง 2 ระบบได้ใบเก่า |
| สวิตช์ใน App Settings (`REQUEST_STATUS_SOURCE`) | deploy แยกจากการสลับ · ย้อนกลับได้ในไม่กี่นาทีโดยไม่ต้อง deploy · โค้ดซับซ้อนขึ้นเล็กน้อย |
| เก็บ `/api/request-status-sims` ไว้ใช้ภายใน | ทดสอบ/เทียบได้โดยไม่แตะเส้นหลัก · เส้นนี้ยังปรากฏใน Swagger ที่เปิดสาธารณะ |
| เก็บ `/order/{serviceOrderNumber}` | ค้นใบงานที่ไม่มี Ticket No ได้ · เพิ่มเส้นใหม่ในสัญญา |

## 4. ผลที่ตามมา

- ใบงานเก่า (F&O) ยังค้นเจอด้วยค่าเดียวกับที่เคยตอบ และใบงานใหม่ (SIMS) ค้นเจอเพิ่ม
- ticket ที่ไม่พบใน SIMS (ใบเก่า หรือไม่มีจริง) ช้าเท่าเดิม (รอ Fabric 1–14 วินาที) · ticket ที่พบใน SIMS เร็วขึ้น (~50 ms)
- ticket ที่ใช้ร่วมหลายใบงานใน SIMS ได้ใบล่าสุดเสมอ (เดิมไม่แน่นอน) · ฝั่ง F&O คงพฤติกรรมเดิมของ SP
- ใบงานที่ไม่มี Ticket No ค้นผ่าน API ไม่ได้ (ไม่มี `/order` แล้ว)
- เส้นที่ลูกค้าใช้ **ขึ้นกับ 2 ระบบ**:
  - SIMS (ทีม SIMS ดูแล): firewall ของฐานข้อมูล (IP ขาออกของ Web App ต้องอยู่ใน rule), credential (ณ วันตัดสินใจยังใช้ของแอป SIMS เอง ยังไม่มี role อ่านอย่างเดียว), ความเร็ว (pool ฝั่งเรา 2 connection)
  - F&O / Fabric mirror: ต้องเปิดอยู่ตราบที่ยังต้องตอบ ticket เก่า — ถ้า Fabric หยุดตอบ (ปิด, ล่ม, throttle หรือ `AZURE_CLIENT_SECRET` หมดอายุ) **ทุก ticket ที่ไม่พบใน SIMS ได้ 500 แทน NOT_FOUND** รวม ticket ที่ไม่มีจริง · **ก่อนปิด F&O หรือ mirror ต้องตัดสินใจก่อน**: เอาการค้น F&O ออกจากโค้ด หรือคง mirror ไว้
  - รายละเอียดและสิ่งที่ต้องทำใน `AS-request-status.md` ข้อ 5
- **ลำดับ deploy บังคับ**: ก่อน merge ต้องตั้ง `SIMS_DB_*` + `SIMS_DB_SSL_CA` ของ Web App ให้ชี้ฐานข้อมูลที่แอป SIMS ใช้งานจริง และยืนยันด้วย ticket จริงก่อน — ถ้าชี้ผิดตัว ใบงานใหม่จะได้ `NOT_FOUND` ทันทีที่ deploy (push `main` = deploy production) · **สถานะ 2026-11-02: ตั้งค่าแล้ว และยืนยันบน production ผ่านเส้น `/api/request-status-sims` (ยังไม่ถูกลบจนกว่าจะ merge) ด้วย ticket จริงได้ `SUCCESS`**
- **ย้อนกลับ** = revert commit แล้ว deploy ใหม่ — ได้สถานะก่อน PR นี้: `/api/request-status` อ่าน F&O อย่างเดียว (ใบงาน SIMS ตั้งแต่ 2026-11-01 ตอบ `NOT_FOUND` ทุกใบ) และเส้น `/api/request-status-sims` + `/order` กลับมา (ต้องคง `SIMS_DB_*` ไว้) · ใช้เมื่อโค้ดใหม่ตอบผิดสัญญาเท่านั้น — ถ้าแค่ SIMS ล่ม ไม่ต้อง revert เพราะใบเก่ายังตอบจาก F&O · method `getRequestStatus` / `postRequestStatus` เดิมใน `fsrProtalController_graphql.js` ไม่ได้ผูก route แล้ว (ฝั่ง F&O เรียก `graphqlService.executeReferencedPoNumber` ตรง) — เก็บไว้จนกว่าจะยืนยันว่าไม่ย้อน แล้วค่อยลบ
